## 1. 프로젝트 목표와 범위

### 1.1 목표

국내(코스피/코스닥) 주식시장에서 특정 세력(작전세력, 큰손, 기관 수급 주체 등)이 매집 중이거나 매도(이탈)하고 있는 것으로 **의심되는** 종목을 정량적 지표 기반으로 스크리닝하고, 해당 종목이 매집(Accumulation) → 상승(Markup) → 분산(Distribution) → 하락(Markdown) 중 어느 국면에 있을 가능성이 높은지를 점수화하여 사용자에게 참고 정보로 제공하는 프로그램을 만든다.

**중요한 용어 정의**: 이 문서에서 "세력주 판단", "매수·매도 시점 예측"이라는 표현은 **확정적 사실 판단이나 미래 예측이 아니라, 과거 데이터 패턴에 기반한 확률적 신호(스코어) 산출**을 의미한다. 프로그램의 출력값은 항상 "~일 가능성이 있다", "~신호가 관측됨" 형태의 확률적/조건부 표현으로 제공되어야 하며, "이 종목은 세력주다", "지금 사라/팔아라" 같은 단정적 문구를 출력하지 않는다.

### 1.2 범위 (In-scope)

- 국내 상장 종목(코스피, 코스닥, 코넥스는 선택)의 시세·수급·공시 데이터 수집
- 아래 1.4의 세력주 판단 지표 계산
- 지표를 종합한 스코어링(세력 개입 의심 지수) 및 국면(매집/상승/분산/하락) 추정
- 과거 데이터 기반 백테스트 및 검증
- 스크리닝 결과를 보여주는 대시보드/스크리너 UI
- 조건 충족 시 사용자에게 알림(텔레그램 등)을 보내는 기능 (알림 = 정보 제공, 주문 실행 아님)

### 1.3 범위 밖 (Out-of-scope, 명시적으로 하지 않는 것)

- **자동 주문 실행(자동매매)**: 실제 매수/매도 주문을 API로 자동 전송하는 기능은 이 프로젝트에서 만들지 않는다. 증권사 Open API를 계좌 조회·시세 조회 목적으로만 사용한다.
- **불특정 다수 대상 유료 신호 판매/배포**: 이 프로그램의 산출물을 제3자에게 유료로 판매하거나 리딩방 형태로 운영하는 것은 범위 밖이다. (법적으로 유사투자자문업 등록 등 별도 규제 대상이 되므로, 그런 사업화를 원한다면 이 문서와 별개로 법률 검토가 선행되어야 한다.)
- **실제 세력의 신원 특정**: "어떤 계좌/누가 세력인지"를 특정하는 기능은 만들지 않는다. 데이터 접근 권한과 개인정보보호법상 불가능하며 필요하지도 않다. 오직 가격·거래량·수급 등 공개된 시장 데이터의 패턴만 다룬다.
- **고빈도 매매(HFT), 초단타 스캘핑용 초저지연 시스템**: 이 프로젝트는 초단위 지연이 중요한 HFT가 아니라 분~일 단위 스윙/스윙성 세력주 관찰을 목표로 한다.

### 1.4 세력주 판단 지표 (핵심 정의)

아래 지표들은 국내 증권사 HTS/MTS 보조지표, 금융 커뮤니티·블로그, 퀀트 커뮤니티 자료를 교차 조사하여 정리한 것이다(출처는 11장 참고). 각 지표는 단독으로는 신뢰도가 낮고, **반드시 여러 지표를 조합**해야 한다는 것이 조사된 자료들의 공통된 결론이다.

#### (A) 거래량 기반 지표
- **거래량 급증률**: 당일(또는 특정 봉) 거래량 ÷ 최근 N일(예: 20일) 평균 거래량. 여러 출처에서 "평균 대비 300% 이상"을 단타 세력 개입 의심 기준으로 언급.
- **거래량-가격 다이버전스**: 주가는 횡보/하락하는데 거래량(또는 AD Line 유사 누적지표)이 증가하는 구간 → 매집 의심 신호.
- **저점 재테스트 시 거래량 감소**: 동일한 지지선을 다시 테스트할 때 거래량이 이전보다 줄어들면 매집이 상당 부분 끝났다는 신호로 해석되는 경우가 많음.
- **장대 양봉 + 거래량 폭증 조합**: 특히 이전까지 거래가 뜸했던 소형주에서 발생 시 주목도가 높음.

#### (B) 수급주체별 매매동향 (외국인/기관/개인)
- **기관+외국인 동반 순매수 연속일수 및 누적 순매수 대금**
- **개인 순매수 급증과 기관/외국인 순매도 전환의 동시 발생** — 조사된 사례(테마주 급등기 분석)에서 "개인이 몰릴 때 기관/외국인이 물량을 넘기는" 패턴이 반복적으로 관찰됨 → 분산(Distribution) 국면 신호로 활용 가능.
- **프로그램매매 순매수 동향** (차익/비차익 구분 가능하면 추가)
- **상위 거래원(브로커) 집중도**: 특정 소수 증권사 창구를 통해 매수/매도가 집중되는 경우 특정 주체의 조직적 매매 가능성 신호로 활용(단, 데이터 접근 제약이 있어 Phase 2 이후 과제로 분류 권장).

#### (C) 신용잔고·공매도 지표
- **신용거래융자잔고 및 잔고율(비율) 증가 추이**: 단기 급등 시 신용잔고가 급증하면 향후 반대매매(강제청산) 리스크가 커져 급락 트리거가 될 수 있음.
- **공매도 잔고/거래대금 비중 변화**: 공매도 잔고 급증은 하락 베팅 증가 신호, 공매도 잔고 감소(숏커버링)는 반등 신호로 활용 가능.
- **대차잔고 대비 공매도 잔고 비율 변화**: 대차잔고는 늘고 공매도 잔고는 유지/감소 → 물량 확보(매집) 가능성으로 해석하는 자료 존재(교차검증 필요, 신뢰도 중간).

#### (D) 호가잔량·체결강도 지표
- **체결강도** = (매수 체결량 ÷ 매도 체결량) × 100. 100% 초과 지속 시 매수세 우위, 150% 이상 구간에서의 유지·이탈 여부가 국면 전환 신호로 자주 언급됨.
- **호가 잔량 불균형**: 매수잔량/매도잔량 비율. 단, "주가 하락 중 매수잔량이 많다"는 것은 오히려 매도벽으로 위장된 허수일 수 있어 **잔량(의도)과 실제 체결(행동)의 불일치**를 함께 봐야 한다는 것이 조사 자료의 공통 지적.
- **대량 체결(블록딜성 체결) 포착**: 특정 호가에서 비정상적으로 큰 단일 체결이 반복되는지 여부.

#### (E) VI(변동성완화장치) 발동 이력
- **동적 VI**: 코스피200 종목 직전 체결가 대비 3%, 그 외 종목/코스닥 6% 이상 변동 시 발동, 2분간 단일가매매 전환.
- **정적 VI**: 전일 종가 대비 10% 이상 변동 시 발동.
- 활용 방식: 특정 종목의 최근 N개월 VI 발동 횟수·발동 시간대(장초반/장중/장마감 동시호가 직전 등)를 지표화. 발동 빈도가 급증하는 시점을 상승(Markup) 국면 진입의 보조 신호로 사용.

#### (F) 캔들/이동평균선 패턴
- **정배열 전환**: 5일선 > 20일선 > 60일선 > 120일선 형태로 전환되는 시점. 60일선 위 안착은 중기 매집 세력의 주도권 장악 신호로 해석되는 경우가 많음.
- **눌림목(단기 조정 후 저점 상승)** 패턴: 저점이 계단식으로 올라가는 형태 → 매집 종료 및 상승 임박 신호로 해석.
- **긴 아래꼬리 + 거래량 동반**: 특정 구간의 매물대를 세력이 흡수하고 있다는 신호로 해석되는 경우가 많음(단, 노이즈가 커서 단독 사용 금지, 다른 지표와 조합 필수).

#### (G) 공시·뉴스 이벤트 연계
- **공시(DART) 발표 시점과 거래량/주가 급등 시점의 시차 분석**: 공시 발표 "이전"에 이미 거래량이 튀는 경우, 정보 선(先)반영 의심 신호로 플래깅(단, 이는 탐지·기록의 목적이며 위법 여부를 프로그램이 판정하지 않는다 — 2장 참고).
- **테마 편입 여부**: 정치/정책/산업 테마 편입 시 실적 개선 없이 수급만으로 급등하는 경우가 많다는 것이 조사된 자료의 공통 지적. 테마 라벨링은 KRX 업종 분류, 뉴스 키워드 클러스터링으로 근사 가능.
- **유통주식수/시가총액 규모**: 세력주는 대체로 유통물량이 적은 중소형주에서 나타나는 경향이 있어, 시가총액·유통비율을 필터 조건으로 사용.

### 1.5 종합 스코어링 및 국면 추정 아이디어 (구현 세션에서 구체화할 것)

와이코프(Wyckoff) 매집/분산 이론의 4국면 프레임을 참고하여 아래와 같이 국면을 정의할 수 있다 (구현 세션에서 임계값은 백테스트로 튜닝):

| 국면 | 특징 조합 (예시) |
|---|---|
| 매집(Accumulation) | 장기 횡보 + 거래량 서서히 증가 + 기관/외국인 순매수 전환 + 저점 완만한 상승 + 신용잔고 안정 |
| 상승(Markup) | 거래량 폭발적 증가 + 동적 VI 발동 빈발 + 체결강도 150%↑ 지속 + 정배열 전환 |
| 분산(Distribution) | 고점권 거래량 유지되나 상승폭 둔화 + 체결강도 100% 하회 전환 + 기관/외국인 순매도 전환 + 개인 순매수 급증 |
| 하락(Markdown) | 거래량 감소 속 하락 지속 + 신용잔고 급감(반대매매 추정) + 공매도 잔고 증가 |

각 지표를 정규화(z-score 또는 백분위 랭크)한 뒤 가중합으로 "세력 개입 의심 지수(0~100)"를 산출하고, 최근 지표 조합 패턴을 규칙기반(rule-based) 또는 간단한 분류 모델(로지스틱회귀, 그래디언트부스팅 등)로 국면 라벨에 매핑하는 방식을 1차 설계안으로 제안한다. 가중치와 임계값은 반드시 6장의 백테스트로 검증 후 확정한다.

## 2. 법적/윤리적 고지사항 및 가드레일 (필수, 최우선 원칙)

> 이 섹션은 프로젝트 전체에서 예외 없이 지켜야 하는 최상위 규칙이다. 아래 항목과 충돌하는 기능 요청이 있으면, 구현 세션은 반드시 사용자에게 재확인을 구해야 한다.

1. **투자자문 아님 고지**: 프로그램이 생성하는 모든 리포트, 대시보드, 알림 메시지에는 "본 정보는 투자 참고용으로만 제공되며, 투자 자문이나 매매 추천이 아닙니다. 투자 판단과 그에 따른 책임은 전적으로 이용자 본인에게 있습니다"라는 문구를 표시한다 (README, 대시보드 하단, 알림 메시지 말미 등 노출 지점마다).
2. **자동매매 주문 실행 금지**: 어떤 경우에도 스코어/신호를 근거로 증권사 API에 매수·매도 주문을 자동 전송하는 코드를 만들지 않는다. 알림은 "정보 통지"까지만 하고, 실제 주문은 사용자가 직접 HTS/MTS에서 수행한다.
3. **비영리·개인 사용 한정**: 산출물(스코어, 알림, 리포트)을 불특정 다수에게 대가를 받고 제공(리딩방 등)하지 않는다. 개정 자본시장법상 온라인 양방향 채널(오픈채팅방, 텔레그램 등)을 통한 유료 투자조언 제공은 정식 투자자문업 등록 없이는 불법이며, 위반 시 3년 이하 징역 또는 1억원 이하 벌금 대상이 될 수 있다(11장 출처 참고). 이 프로젝트는 그런 서비스가 아니다.
4. **시세조종 목적 사용 금지 및 무관함 고지**: 이 프로그램은 시세를 관찰·분석하는 도구이지, 시세에 영향을 주거나 타인의 오인을 유도하는 행위(자본시장법 제176조 시세조종행위)와 무관하다. 프로그램 산출물을 이용해 허위 매수·매도 주문을 반복하거나(가장매매, 통정매매 등) 인위적으로 거래량/가격을 조작하는 행위에 사용해서는 안 된다.
5. **확정적 판단 표현 금지**: "이 종목은 세력주다", "지금이 매수 타이밍이다" 같은 단정적 문구를 프로그램이 출력하지 않는다. 항상 "~신호가 관측됨", "~국면일 가능성(스코어 XX)"과 같은 확률적 표현을 사용한다.
6. **데이터 이용약관 준수**: 각 데이터 소스(KRX, DART, 네이버/다음 금융, 증권사 API 등)의 이용약관과 요청 빈도 제한을 준수한다. 과도한 크롤링으로 서버에 부하를 주거나 접근 차단을 유발하는 방식은 금지한다.
7. **오탐(false positive) 가능성 명시**: 스코어링 로직은 확률적 추정이며 실제 세력 개입 여부를 확인해주지 않는다는 점을 문서와 UI에 명확히 고지한다.
8. 위 원칙에 대해 애매한 상황이 발생하면, 구현 세션은 기능을 임의로 확장하지 말고 `project_작업일지.md`에 이슈로 기록한 뒤 사용자에게 확인을 요청한다.

## 4. 프로그램 아키텍처

```
[1] 데이터 수집(Collectors)
     ├─ 배치 수집: 일별 시세, 투자자별 매매동향, 신용잔고, 공매도 잔고, 공시 목록 (pykrx, DART API, KRX)
     └─ 준실시간/실시간 수집: 호가, 체결, VI 발동 이벤트 (증권사 API WebSocket, Phase 2+)
            │
            ▼
[2] 저장(Storage)
     ├─ 원시 데이터: data/raw (일자별 CSV/Parquet)
     └─ 정제 데이터: data/processed (SQLite 또는 DuckDB — MVP 단계에서는 별도 DB 서버 불필요)
            │
            ▼
[3] 지표 계산(Indicators)
     ├─ 거래량 지표 / 수급 지표 / 신용·공매도 지표
     ├─ 호가·체결강도 지표 (실시간 수집 시)
     ├─ VI 이력 지표
     ├─ 캔들·이평선 패턴 지표
     └─ 공시·뉴스 이벤트 연계 지표
            │
            ▼
[4] 스코어링(Scoring) — 세력 개입 의심 지수 + 국면(매집/상승/분산/하락) 추정
            │
            ▼
[5] 산출(Output)
     ├─ 시각화/대시보드 (Streamlit): 스크리닝 테이블 + 종목 상세 차트
     ├─ 알림(Alert Bot): 텔레그램 등으로 스코어 임계값 돌파/국면 전환 통지 (정보 알림, 주문 아님)
     └─ 리포트: 정기 요약 리포트(마크다운/PDF)

[별도 트랙] 백테스트(Backtest): 과거 데이터로 스코어링/국면 추정 로직 검증 (6장)
```

설계 원칙:
- 수집(Collectors), 지표(Indicators), 스코어링(Scoring), 출력(Output)은 서로 독립적인 모듈로 분리하여 재사용성과 테스트 용이성을 확보한다.
- 배치(일 단위) 파이프라인을 먼저 안정화한 뒤, 실시간 요소를 단계적으로 추가한다(5장 로드맵).
- 공시 데이터는 반드시 "발표 시각" 기준으로 시점 정합성을 유지한다(사후에 알게 된 정보를 과거 시점 분석에 사용하지 않도록 주의 — 6장 백테스트에서 특히 중요).

## 5. 산출물 형태 정의

| Phase | 산출물 | 내용 | 채택 이유 |
|---|---|---|---|
| Phase 1 (MVP) | 배치 스크리너 + 정적 대시보드 (Streamlit) | 장 마감 후(EOD) 데이터로 전 종목 스코어링, 상위 N개 종목을 테이블/차트로 제공 | 실시간 인프라 없이 빠르게 핵심 로직(지표·스코어링)을 검증할 수 있음. 초기 구축 난이도와 비용이 가장 낮음 |
| Phase 2 | 준실시간 대시보드 | 장중 폴링(예: 1~5분 주기)으로 주요 지표 갱신 | 실시간 웹소켓 없이도 체감 지연을 크게 줄일 수 있음 |
| Phase 3 | 알림 봇 (텔레그램) | 스코어 임계값 돌파/국면 전환 시 알림 발송 | 사용자가 대시보드를 계속 지켜보지 않아도 되는 편의성 제공 |
| Phase 4 | 실시간 대시보드 (WebSocket 기반) | 호가/체결 실시간 반영 | 지연 최소화가 필요할 때만 고려. 인프라 복잡도·비용이 가장 크므로 Phase 1~3 안정화 이후 판단 |

**MVP로 "배치 스크리너+대시보드"를 권장하는 이유**: (1) 세력주 판단 지표 상당수(신용잔고, 공매도 잔고, 투자자별 매매동향, 공시)가 애초에 일 단위로만 갱신되어 실시간성의 이점이 제한적이고, (2) 실시간 인프라(웹소켓, 지연 관리)는 개발 난이도와 유지보수 비용이 커서 로직 검증 전에 투자하는 것은 비효율적이며, (3) 개인 프로젝트 규모에서 관리 가능한 범위이기 때문이다.

## 6. 백테스트 및 검증 방법론

1. **유니버스 구성**: 상장폐지·관리종목 전환 종목도 포함한 과거 시점 유니버스를 사용해 생존편향(survivorship bias)을 방지한다.
2. **시점 정합성(Point-in-time correctness)**: 공시·재무데이터는 실제 "공표 시각" 기준으로만 사용한다. 특히 분기 실적, 사업보고서 등은 발표 지연을 반드시 반영한다(사후 확정치를 과거 시점에 알고 있었던 것처럼 사용하는 lookahead bias 금지).
3. **기간 분리**: 학습(파라미터 튜닝) 구간과 검증(out-of-sample) 구간을 분리하고, 가능하면 워크포워드(walk-forward) 방식으로 검증한다.
4. **성과 지표**: 스코어 임계값별 가상매매 시뮬레이션 결과에 대해 승률, 평균 수익률, MDD(최대낙폭), 샤프비율을 계산하고, 코스피/코스닥 지수 및 무작위 종목 선택 대비 초과 성과를 비교한다.
5. **거래비용 반영**: 수수료, 세금(거래세), 슬리피지를 반영한다. 특히 세력주 후보는 유동성이 낮은 소형주가 많아 슬리피지를 보수적으로(과다하게 유리한 가정 금지) 설정한다.
6. **과최적화 방지**: 지표 가중치·임계값을 과거 데이터에 지나치게 맞추지 않도록 파라미터 수를 최소화하고, 교차검증 결과의 안정성을 확인한다.
7. **정성적 사례 검증**: 정량 백테스트와 별개로, 과거에 실제로 급등락했던 대표 사례 몇 건을 선정해 프로그램의 국면 추정이 실제 흐름과 부합하는지 수동으로 점검한다.
8. **백테스트 결과와 실거래 성과의 괴리 고지**: 백테스트 성과가 실제 미래 성과를 보장하지 않는다는 점을 리포트에 명시한다.

권장 도구: pandas 기반 자체 시뮬레이션(유연성) 또는 vectorbt(속도), 실거래 로직과 유사한 형태 검증이 필요하면 backtrader / Backtesting.py 고려(11장 출처 참고).

## 8. 작업 방식 규칙

### 8.1 `project_작업일지.md` 작성 규칙
- 폴더 생성 직후 가장 먼저 이 파일을 만든다.
- 매 세션 시작 시 최상단(또는 지정된 위치)에 `## YYYY-MM-DD HH:MM 세션 시작` 헤더를 추가한다.
- 파일을 하나 생성하거나 의미 있게 수정할 때마다 다음 형식으로 기록한다: `- [파일 경로] : [수행한 작업 요약] : [상태: 진행중/완료/보류]`
- 리서치를 추가로 수행한 경우 무엇을 검색했고 어떤 결론에 도달했는지 요약을 남긴다.
- 세션을 종료할 때는 `### 다음 세션에서 할 일`을 명시적으로 남긴다.

### 8.2 파일 크기 및 분할 규칙
- 하나의 파일이 18KB를 넘을 것으로 예상되면, 설계 단계에서 미리 책임(역할) 단위로 2~3개 이상 파일로 나눈다.
- 분할 기준 예시: 데이터 소스별(collector_*.py), 지표 카테고리별(indicator_*.py), 기능 단위별(scoring vs backtest vs dashboard).
- 함수/클래스가 지나치게 길어지면(대략 300~400줄 초과) 하위 모듈로 추출하는 것을 원칙으로 한다.

### 8.3 세션 재개 규칙
- 새 개발 세션을 시작할 때는 항상 `project_작업일지.md`의 가장 최근 항목과 "다음 세션에서 할 일"을 먼저 읽고 그 지점부터 작업을 이어간다.
- 작업일지에 기록되지 않은 임의의 작업으로 건너뛰지 않는다.
- 이 지침서(스펙 문서) 자체가 변경되어야 할 필요가 발견되면, 지침서를 직접 고치지 말고 `docs/` 하위에 변경 제안을 기록한 뒤 사용자 확인을 받는다.

## 9. 보안 규칙

1. API 키, 계좌번호, 접근토큰(access token), 시크릿 등은 **코드에 절대 하드코딩하지 않는다.**
2. 모든 민감정보는 `.env` 파일 + `python-dotenv` 등으로 로드하고, `.env`는 `.gitignore`에 반드시 포함한다.
3. `.env.example`을 만들어 어떤 환경변수가 필요한지 키 이름만 공유한다(값은 비워둠).
4. `config/settings.yaml` 등 설정 파일에는 키 값을 직접 쓰지 않고 `${ENV_VAR}` 형태로 환경변수를 참조하도록 설계한다.
5. 로그 파일(`logs/`)에 API 키, 계좌번호, 토큰 등이 그대로 출력되지 않도록 마스킹 처리한다.
6. `data/`, `.env`, `logs/` 등 민감하거나 용량이 큰 디렉토리는 `.gitignore`에 포함한다.
7. 증권사 API의 주문 관련 스코프(권한)는 애초에 신청하지 않거나, 신청하더라도 코드에서 주문 함수를 호출하지 않는다(2장 원칙과 연결).

## 10. 리스크 및 한계 (구현 세션이 인지해야 할 것)

- 스크래핑 기반 소스(네이버/다음 금융, pykrx 일부 기능)는 대상 사이트의 구조 변경 시 언제든 깨질 수 있다. 예외처리와 모니터링이 필요하다.
- 소형주는 유동성이 낮아 실제 체결 가능성과 백테스트상의 가정이 크게 다를 수 있다.
- VI, 체결강도, 호가잔량 등 장중 데이터는 무료로 안정적인 실시간 소스를 구하기가 상대적으로 어렵고, 증권사 API 의존도가 높아진다.
- 지표 조합에 의한 스코어링은 본질적으로 사후적(rear-view) 패턴 인식이며, 새로운 유형의 작전 수법에는 뒤늦게 반응하거나 오탐할 수 있다.
- 공시·뉴스 텍스트 분석(NLP)을 고도화하려면 별도의 데이터셋과 모델 검증이 필요하며, 이 지침서는 1차 규칙기반 접근을 우선 제안한다.
